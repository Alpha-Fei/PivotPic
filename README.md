# 枢图 PivotPic

监听指定文件夹，把**横版图片自动旋转 90° 变成竖版**，常驻系统托盘在后台运行。

Windows 10 1809+ / Windows 11 · C# 12 · .NET 8 · WPF · 零第三方依赖 · 单文件 exe

---

## 它解决什么问题

整理素材时，横竖版混在一起手动转很烦。这个工具丢在后台，往指定文件夹里丢图，横版自动转正，竖版一动不动。顺带还能盯着分辨率——超过阈值就弹卡片提醒，点一下就定位到文件。

## 功能

| 能力 | 说明 |
|---|---|
| 自动转向 | 逻辑尺寸宽 > 高即判定横版，顺时针转 90°；**按 EXIF 校正后的尺寸判定**，手机竖拍照片不会被转错 |
| 多目录监控 | 最多 32 个目录，逐个独立启停 |
| **路径可编辑** | 双击路径打开「目录设置」，在首张卡片里手写带占位符的模板；输入时实时显示展开结果，可直接浏览目录或一键把日期转成占位符 |
| **处理进度提示** | 开始处理时屏幕底部浮出独立进度卡片（主窗口隐藏到托盘时同样可见），进度条按「已处理 / 本轮总数」实际填充并显示 `3 / 8 · 文件名.png`；一批干完显示「处理完毕，共 N 个文件 · 旋转 M 张」后自动淡出。设置里可关闭，默认开启 |
| 子文件夹开关 | 每个目录独立控制是否递归，默认开启 |
| 分辨率巡检 | 每个目录独立开关（默认关闭），阈值默认 300；支持长边像素 / 短边像素 / 总像素 / 文件体积四种口径 |
| 超标提醒 | 右下角自绘卡片 + 托盘角标 + 卡片徽标；一键在资源管理器定位；同文件 24 小时内不重复提醒 |
| 系统托盘 | 三态图标（空闲 / 监控中 / 告警），全部由矢量几何运行时渲染 |
| 禁止双开 | 命名互斥量 + 命名管道，第二次启动会把已有窗口唤到前台 |
| 时间占位符 | 路径里可写 `{mm-dd}`，每天自动切到新日期目录 |
| 启动补扫 | 程序没运行时放进来的图片，下次启动会补处理，不会漏 |
| 配置容错 | 配置文件损坏时自动备份并回退默认，不会起不来 |
| **在线更新** | 启动后静默检查新版本，发现即弹「更新详情」；一键下载 → SHA256 校验 → 拉起安装包并自动等待旧进程退出 |
| **内置加速** | 网络访问 GitHub 不稳时自动启用本机加速通道（只接管 GitHub 域名），关闭或退出时还原系统设置；用户无需配置、无需安装任何东西 |

## 路径占位符

| 写法 | 展开结果（2026-11-04 09:15:32） |
|---|---|
| `{mm-dd}` | `11-04` |
| `{yyyy}-{mm}-{dd}` | `2026-11-04` |
| `{yyyyMMdd}` | `20261104` |
| `{HH}-{mi}-{ss}` | `09-15-32` |

- **`mm` 表示月份，`mi` 表示分钟**。同一对花括号内出现过 `hh`/`HH` 之后，后面的 `mm` 视为分钟（所以 `{yyyy-MM-dd_HHmmss}` → `2026-11-04_091532`）；跨花括号不传递。
- `%USERPROFILE%` 这类环境变量会先展开。
- 编辑路径时**边输边看**：输入框下方会实时显示"预览：`D://图库//2026-11-04`"，写错占位符会立刻变黄提示，不用保存后才发现。
- 写错的占位符（如 `{xyz}`）原样保留，并在卡片上给出黄色提示，不会静默消失。

## 构建

需要 **.NET 8 SDK**。本机若未全局安装，本项目脚本会使用 `%USERPROFILE%\.dotnet` 下的 SDK。

```bat
:: 调试运行
dotnet build src\PivotPic\PivotPic.csproj
dotnet run   --project src\PivotPic\PivotPic.csproj

:: 发布单文件 exe（目标机器无需装 .NET）
build.cmd
```

产物在 `dist\PivotPic.exe`，**实测 64 MB**（开启单文件压缩），单文件自包含，目标机器无需安装 .NET。

### 构建排错

`--self-contained -r win-x64` 需要还原 runtime pack，国内网络下 `api.nuget.org` 常返回 302 后超时。仓库内 `nuget.config` 已指向华为云镜像；若镜像也不可用，可改用**离线还原**——包其实早已在全局缓存里，卡的是联网探测：

```bat
dotnet publish src\PivotPic\PivotPic.csproj -c Release -r win-x64 --self-contained true ^
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true ^
  --source "%TEMP%\empty-nuget" -o dist
```

（先建一个空目录当包源。缺包会立刻报错，比 302 循环等三分钟好排查。）

> 注意：本机 `dotnet` 在 `C:\Program Files\dotnet`（只有 10.x 运行时），SDK 装在 `%USERPROFILE%\.dotnet`。因此 `--self-contained false` 在这类环境**不可用**——apphost 只认机器级安装目录，找不到用户目录里的 8.0.33。

### 单文件构建的三个已知现象

1. **不压缩变体会散出文件**：若漏了 `IncludeNativeLibrariesForSelfExtract=true`，`dist` 下会多出 5 个原生 DLL，不再是单文件。
2. **R2R 与单文件互斥**：不要同时开 `PublishReadyToRun=true`，两者冲突会构建失败。
3. **首次启动可能被拦**：64 MB 自解压 exe 是杀软重点观察对象，首次运行若被拦，添加排除即可（Release 版无签名，属正常现象）。

## 关键实现说明

**为什么旋转要按 EXIF 校正后的尺寸判断**
手机竖拍的照片，像素是 `800×600`（横向），但 EXIF 里写着 `Orientation=6`，看图软件会转 90° 显示成竖版。如果直接按像素宽高判定，会把它当成横版再转一次，结果照片躺倒。

**为什么改完文件不会被自己再次触发**
`FileSystemWatcher` 会监听本进程的写入。旋转完成 → 触发事件 → 再旋转，CPU 瞬间打满。`IgnoreSet` 在**打开写流之前**登记该文件指纹（TTL 8 秒），消费端命中就直接丢弃事件。

**为什么读大文件要两次采样**
从 U 盘拖入 50MB 图片时，文件刚创建只有几 MB，此时解码会失败或得到半截图。队列消费时先等 400ms，再连续两次采样（间隔 250ms）尺寸不变且能独占打开，才认为写入完成。

## 已知限制

1. **WebP 只能读不能写**：Windows 的 WIC 管线没有 WebP 编码器（解码也要系统装扩展），遇到 WebP 横版图会跳过并记日志。
2. **JPEG 物理旋转会重编码**：`QualityLevel=95` + 保留 EXIF/ICC/DPI，但严格来说不是无损。若只想改显示方向，可在设置里切「仅改写 EXIF 标记」——零画质损失，但部分老软件读不出方向。
3. **时间占位符跨零点**：定时器在 00:00:10 重新解析路径，零点后 10 秒内落进旧目录的文件仍归旧目录。
4. **「今日处理」统计不含已轮转的日志文件**：单日日志超过 5MB 后，早期记录会被轮转，统计可能少算。
5. **镜像翻转的 EXIF 方向（2/4/5/7）未处理**：按未翻转处理并在日志标注，此类图片极少见。
6. **配置文件损坏时监控目录会清空**：程序把坏文件重命名为 `config.broken.{时间戳}.json` 后回退默认配置，目录列表需要重新添加。原始内容在那个备份里，可手工恢复。
7. **日志目录被外部移走后会自动重建**：`LogService` 每次写入前都会 `CreateDirectory`，所以手工把 `logs` 改名或删掉，下一次写日志时它会重新出现。这是自愈行为，不是故障。
8. **界面不显示「待处理文件数」**：服务层目前只提供「正在处理中的目录数」，这是**活动指示**，不是积压计数 —— 两者是不同指标，不是精度差异。真实积压量 = 队列 `Count` + (是否正在处理 ? 1 : 0)，in-flight 那一张可能因稳定检测占住数秒，直接把 `Count` 当「队列 N」显示会让人误以为卡住。状态栏因此显示「目录 N 个」。要真正展示积压量需引入新指标，属需求侧变更。

## 排错经验：判断「缺了」之前，先确认三件事

这份代码在开发过程中有三次差点被误判成"缺陷"，都是同一类思维跳跃。记在这里，比记结论有用：

1. **空间** —— 这个位置是不是该负责的地方？
   反例：grep 到 `SettingsPage` 里没有 `Tray.UpdateState`，就断定"该路径漏通知"。实际总开关在 `MonitorPage`，`MonitorPage.xaml.cs:353` 先写配置、`:369` 后通知托盘，顺序本来就是对的。
2. **可得** —— 这个能力是不是真的不存在？
   反例：看到 `MonitorService._queue` 是私有成员就断定"队列深度拿不到"。实际 `Channel.CreateUnbounded` 下 `CanCount == true`，`_queue.Reader.Count` 可用；卡点在冻结的接口契约，不在能力。
3. **语义** —— 拿到的结果是不是你说的那个含义？
   反例：即便拿到了 `Count`，它也不含"正在处理中的那一张"，作为「队列 N」展示会少 1，让"正在处理最后一张"被读成"队列 0 却卡住"。

前两问都会让人停下来去查；**第三问最危险，因为数字一旦能打印出来，看起来就已经"对"了。**

> 若要把「队列 N」接回界面，需同时满足两个前提：① `Reader.Count` 只在 unbounded channel 下可用，改有界加背压后会抛 `NotSupportedException`，那时必须由服务自己维护计数；② 必须补上 in-flight 的那 1。这两条已写死在 `Views/MonitorPage.xaml.cs` 的 `QueueDepth` 注释里。

## 品牌视觉

图标与标题标识均来自 `pivopiv` 矢量标识：紫色圆角方块（`#5546E8`）+ 白色镂空 P + 薄荷绿状态点（`#BDF9CF`）。强调色全站统一使用品牌紫，深色与浅色主题各有一套明度适配。

- `Assets/app.ico` —— 多尺寸应用图标，编译进 exe，资源管理器中直接可见
- `Themes/Icons.xaml` 中的 `Image.Brand` / `Image.BrandSymbol` —— 矢量绘制，标题栏与关于页共用
- 托盘图标在运行时按 16/20/24/32/48/256 六种尺寸渲染同一段几何，状态点颜色表示空闲 / 监控中 / 告警

## 界面

深色优先，跟随系统主题。全部图标为手写 `StreamGeometry`，工程内没有任何 `.ico` / `.png` / 字体图标；托盘图标在运行时由同一段几何渲染成 16/20/24/32/48/256 六帧 ICO。

动效统一 160/240ms `CubicEase EaseOut`，只对 `Opacity` 与 `TranslateTransform` 做动画，不触发布局重排。

## 在线更新

- 启动后延迟数秒静默检查，之后每 24 小时一次；检查走**直连优先**（元数据是几 KB，直连更快），链路不通才切内置加速。
- 发现新版本弹「更新详情」：版本对比、发布日期、更新说明、包大小；「稍后」后同一版本不再打扰，主窗底部保留横幅入口。
- 下载顺序：内置加速 → 第三方镜像 → 直连；断点续传（`.part` + `Range`），下载完按 `checksums.txt` 校验 SHA256，不一致立即删包并拒绝执行。
- 安装：以 `--wait-pid` 启动安装包，等当前进程退出后再解压，避免文件占用。
- 失败不影响主功能：加速起不来就直连，检查失败只写日志并在设置页显示「上次检查」结果。
